1. What is this dashboard and why does it exist?

The DMN TCK (Decision Model and Notation Technology Compatibility Kit) is a public test suite maintained at github.com/dmn-tck/tck. It contains thousands of test cases that check whether a DMN engine correctly implements the specification. Various contributors open Pull Requests (PRs) to that repository adding new test cases.

Our engine is Apache KIE Drools 999-SNAPSHOT (the in-development next version). The question we need to answer continuously is:

For every open PR in the upstream TCK repo — if that PR were merged today, how many of its new test cases would Drools pass or fail?

Answering this manually would require a developer to check out each PR, build Drools from source, run the tests, and interpret the results. The dashboard automates all of that and presents the answer as a web page that refreshes itself daily.

The live dashboard is at: https://athirahari77.github.io/tck/drools-dashboard.html

2. The moving pieces — what files do what

FileWhat it does
.github/workflows/pr-test.yml The main automation. Runs on GitHub's servers. Polls for open PRs, builds Drools, runs tests, saves results, and regenerates the dashboard HTML.
.github/workflows/sync-upstream.yml Every day, pulls the latest changes from the upstream dmn-tck/tck master branch into our fork. This keeps our copy of the test cases up to date.
scripts/generate_dashboard.py A Python script that reads the saved test results and produces the HTML dashboard page. It is not a web server — it runs once, produces one HTML file, then exits.
TestResults/Drools/999-SNAPSHOT/tck_results.csv The baseline — a CSV file recording which tests fail on master before any PR is applied. This is the reference point for deciding whether a PR introduces new failures.
pr-results/<PR_NUMBER>/tck_results.csv The test results for a specific PR. One folder per PR. Created by CI after running the tests against that PR's code.
pr-results/<PR_NUMBER>/meta.json Metadata about a PR test run: when it ran, which Drools commit was used, pass/fail counts, and whether there was a merge conflict.
docs/drools-dashboard.html The output file that gets served as the website. Generated by the Python script. Never edited by hand.

3. The CI workflow step by step

.github/workflows/pr-test.yml

This workflow is the heart of the system. Here is what it does, one step at a time.

1
Check out our repository

GitHub's CI server starts with a blank machine. This step downloads the tck_dashboard branch of our fork onto that machine so subsequent steps can read and write files.

The fetch-depth: 0 setting means it downloads the full git history, not just the latest commit. This is needed so that the final git push back to tck_dashboard works reliably — shallow clones can cause push rejections when the remote has moved ahead. The branch merging happens inside the throwaway upstream clones (step 7), not here.

2
Decide what to do (run mode)

The workflow can be triggered in three different ways and needs to behave differently for each:

  • Scheduled (automatic, daily at 2am UTC): Ask the GitHub API for all open PRs in the upstream TCK repo. Test any PR that either has no saved results yet, or whose current head SHA on GitHub differs from the SHA stored in its meta.json — meaning the author has pushed new commits since the last test run.
  • Push (automatic, when test cases change): Re-test all open PRs because the master test cases have changed and old results might now be stale.
  • Manual (you click "Run workflow" on GitHub): Either test one specific PR number you type in, test all open PRs, or just regenerate the dashboard HTML from existing saved results without running any tests.

The result of this step is a variable called pr_list — a space-separated list of PR numbers to test (e.g. 717 720 737), and a flag should_test that is either true or false.

3
Set up Java 17

Drools is a Java project. The CI machine starts with no Java installed. This step installs Java 17 (Temurin distribution) so Maven can compile and run Drools. This step is skipped entirely if there are no PRs to test.

4
Find the current Drools source commit

We ask the Drools GitHub repository: "what is your latest commit hash?" and save the first 12 characters of it (e.g. 456693c0d18c). This is used as a cache key in the next step and also saved in meta.json so we know exactly which version of Drools produced the test results.

5
Cache the Maven download folder

Building Drools requires downloading hundreds of Java library files from the internet. This takes several minutes. The cache step saves those files between CI runs so they only need to be downloaded once per Drools commit. If Drools hasn't changed since last time, the cache is reused and this step is nearly instant.

6
Build Drools from source

This is the most time-consuming step. It clones the full Drools source code from apache/incubator-kie-drools and compiles it.

An important nuance: we do not build the entire Drools repository. The full build fails in CI because some modules depend on a separate repository (incubator-kie-kogito-runtimes) that isn't available. Instead we build only the two modules the TCK runner needs:

-pl kie-dmn/kie-dmn-api,kie-dmn/kie-dmn-core -am

The -pl flag means "project list" — only build these modules. The -am flag means "also make" — also build everything these modules depend on. The result is installed into the local Maven cache (~/.m2) as kie-dmn-core-999-SNAPSHOT.jar, which the TCK runner will pick up automatically.

7
Test each PR in an isolated workspace

This is the core logic. For each PR number in the list, the following happens:

a) Clone the upstream TCK repo into a temporary folder. We download a fresh copy of dmn-tck/tck into a folder named upstream-tck-pr-717 (using the PR number). This is completely separate from our own repository.

b) Fetch the PR's code into that clone. Every open PR on GitHub has a special reference available at pull/717/head. We download just that branch into our temp clone. This is the proposed change — the new test cases the PR author wants to add.

c) Check out the PR branch and merge master into it locally. Here is a key design decision: a PR branch might be days or weeks out of date with master. If we test it as-is, it might fail tests that have nothing to do with the PR — they fail only because the branch is stale. To avoid this noise, we do a local git merge master inside the temp folder. This simulates "what would happen if the PR author synced their branch today." Crucially, this merge only exists inside the throwaway temp folder — it is never pushed anywhere and never affects the PR author's branch. If the merge has conflicts (rare for test-only PRs), we skip the merge and note merge_conflict: true in the results.

d) Run the TCK test runner. We run mvn verify -Pdrools inside the temp clone. Maven finds the kie-dmn-core-999-SNAPSHOT.jar we built in step 6, and runs all the test cases against it. The results are written to a CSV file inside the temp folder.

e) Copy the results back and delete the temp folder. We copy just the CSV file into pr-results/717/tck_results.csv in our own repository, then delete the entire temp folder. Nothing from the upstream PR permanently enters our repository — only the test result numbers.

Pass/fail counts are computed by inspecting column 4 of each CSV row (the status field) using awk, not a full-line text search. This prevents a Java exception message in the fifth column from accidentally inflating the counts. The CSV has no header row, so the total line count equals the total test-case count exactly.

We also write a meta.json file recording: the PR number, title, run date, Drools commit SHA, head SHA, total/pass/fail counts, how many commits behind master the PR was, and whether we had a merge conflict.

f) Commit and push after each PR. Results are saved to git immediately after each PR finishes rather than waiting until the entire loop is done. This means a timeout or runner failure mid-loop only loses the in-progress PR, not every PR tested so far. Each push uses a rebase-retry loop (up to 3 attempts) to handle the case where the remote has moved ahead — for example because a queued run's push landed while this run was mid-loop.

8
Set up Python

The dashboard generator is written in Python. This step installs Python 3.11 and the requests library (used to call the GitHub API to fetch PR details).

9
Generate the dashboard HTML

Runs the Python script scripts/generate_dashboard.py which reads all the saved results and produces a single HTML file at docs/drools-dashboard.html. This step always runs regardless of whether any testing happened — even a "refresh only" run regenerates the page.

10
Commit and push dashboard HTML

After all PRs have been tested (and their individual results already committed per step 7f), this step commits and pushes the regenerated docs/drools-dashboard.html. GitHub Pages then serves the docs/ folder as a website automatically, usually within a minute or two of the push.

4. The dashboard generator (Python script) explained

scripts/generate_dashboard.py

This script reads data from disk and from the GitHub API, then produces one HTML file. It is split into several logical sections.

GitHub API functions

fetch_prs() — calls the GitHub API to get the list of currently open PRs from dmn-tck/tck. Returns a list of PR objects containing title, author, number, URL, and dates.

fetch_pr_files() — for each PR, asks GitHub which files that PR changes. This is used to show which test suites a PR touches (e.g. "this PR adds files in 1157-implicit-conversions/").

pr_new_suites() — filters the file list to only TestCases/compliance-level-*/ paths and extracts the suite folder name. So if a PR touches TestCases/compliance-level-3/0720-imports/ it returns {"0720-imports"}.

CSV parsing

parse_csv() — reads a tck_results.csv file. Each row has: suite path, test name, case ID, status (SUCCESS or ERROR), and failure message. The function returns three things:

  • A dictionary of suite names → pass/fail counts (used for the bar charts)
  • A list of all failures with their details
  • A summary with total/pass/fail numbers

Each failure gets a unique key in the format suite_path::case_id (e.g. compliance-level-3/0068-feel-equality::range_010). This key is how we track "is this the same failure across different runs?"

Baseline loading and failure splitting

load_baseline() — reads the baseline CSV and returns a Python set containing all failure keys. A set is like a list but makes it extremely fast to ask "is this key in here?" for thousands of items.

split_failures() — given a list of failures from a PR test run, splits them into two groups: failures whose key is in the baseline set (pre-existing) and failures whose key is not in the baseline set (new, introduced by the PR).

Loading PR results from disk

load_pr_results() — scans the pr-results/ directory. For each numbered subfolder it finds, it loads the tck_results.csv and meta.json. Returns a dictionary mapping PR number → results data.

Visualisation helpers

_donut_svg() — generates a circular donut chart as an SVG image (pure maths — no external charting library needed). It calculates the arc lengths using the circumference of a circle and stroke-dasharray to draw the green (pass) and red (fail) segments.

_level_bars() / level_bar_rows — generates horizontal bar charts showing pass rates per compliance level and per failing suite. Each bar is a div with a percentage width and a colour (green = 100%, amber = mostly passing, red = mostly failing).

PR status table

_pr_status_table() — builds the main PR table. For each open PR it produces one row with:

  • The PR number and a link to it on GitHub
  • The title, author, and last-updated date
  • Which test suites the PR touches (purple badges)
  • The result: ✗ N new failures or N pre-existing only or ✓ all pass or not tested
  • The pass rate (e.g. "3,396 / 3,403 (99%)")

A coloured left border stripe is added to each row via CSS to make the status visible at a glance.

Net-new failures drill-down

_new_failures_drilldown() — for every PR that has new failures, produces a detailed table showing each individual failing test case: which compliance level, which suite, which case ID, the test name, and the failure message. Pre-existing failures are completely excluded from this section — they are only noted as a count ("3 pre-existing failures excluded from this list"). This section is hidden entirely if no PR has new failures.

Baseline table

_baseline_table() — a simple table listing all failures that exist on upstream master before any PR is applied. These are known Drools issues that we are aware of and that should not be blamed on any PR.

Main build function

build_dashboard() — ties everything together. It loads all the data, computes the metrics, calls all the helper functions to produce HTML fragments, assembles them into a complete HTML document, and writes the file to disk. The resulting file is entirely self-contained — no external CSS or JavaScript libraries, no internet connection needed to view it.

5. The baseline concept — pre-existing vs new failures

This is the most important concept in the whole system. Without it, every PR would appear to fail dozens of tests — not because the PR is bad, but because Drools already has known failures on master.

Analogy: Imagine a car that already has a broken radio before you take it to the mechanic to fix the brakes. After the mechanic returns the car, the radio is still broken. You would not blame the mechanic for the radio — it was broken before they touched it. The baseline is our way of recording "the radio was already broken before any PR touched anything."

The baseline CSV (TestResults/Drools/999-SNAPSHOT/tck_results.csv) was produced by running the full TCK test suite against Drools 999-SNAPSHOT on the current master branch, with no PR applied. It recorded 3 failures:

  • 0068-feel-equality — 2 failures (FEEL equality edge cases)
  • 0085-decision-services — 1 failure (decision service result comparison)

When we test a PR and it shows those same 3 failures, we know the PR did not cause them. When a PR shows additional failures not in that list, those are genuinely introduced by the PR's new test cases that Drools cannot yet pass.

Important: The baseline CSV must only contain results from running against upstream master with no local modifications. If you run tests locally with a PR's test cases applied and then commit that CSV, the baseline becomes polluted with PR-specific failures and the classification breaks. This happened once during development and was fixed by removing the contaminating rows.

6. The sync-before-test trick

Many PR branches in the upstream TCK repo are weeks or months out of date with master. If we test them as-is, we see failures that have nothing to do with the PR — they exist only because the branch hasn't picked up recent changes to master.

Analogy: Imagine someone wrote a book chapter six months ago. Since then, other chapters have been edited and the chapter numbering changed. If you proofread their chapter today without applying those edits first, you'd find chapter-number errors that are not their fault.

Our solution: before running tests, we do a local git merge master inside the throwaway temp folder. This means we test "the PR's changes on top of the current master" — which is what would actually happen if the PR were merged today.

This is completely safe because:

  • The merge only exists inside a temporary folder that is deleted immediately after copying the results out
  • Nothing is ever pushed to the PR author's branch — their GitHub PR is completely untouched
  • If the merge has a conflict (two people edited the same file), we abort the merge and test the raw branch instead, flagging it as merge_conflict: true in the metadata

The footnote on the dashboard reads: "Results tested as if each PR branch were synced with master (local merge before run) — failures shown are genuine conflicts introduced by the PR, not stale-branch noise."

7. Where results are stored

All results are stored as regular files in the git repository itself. There is no separate database.

pr-results/
  717/
    tck_results.csv   ← one row per test, each row is pass or fail
    meta.json         ← metadata about the run
  720/
    tck_results.csv
    meta.json
  ...

TestResults/Drools/999-SNAPSHOT/
  tck_results.csv     ← the baseline (master, no PRs applied)

The meta.json for each PR looks like this:

{
  "pr_number": 717,
  "pr_title": "Add tests for implicit conversions in Decisions, BKMs and DSs.",
  "run_date": "2026-09-09T13:59:42Z",
  "drools_sha": "456693c0d18c",
  "head_sha": "a3f8c12d9e4b7f20c1d6e8a91b3c5f7d2e4a6b8c",
  "total": 3403,
  "pass": 3396,
  "fail": 7,
  "behind_by": 39,
  "sync_status": "diverged",
  "tested_as_synced": true,
  "merge_conflict": false
}
FieldWhat it means
run_dateWhen CI ran this test
drools_shaThe exact Drools commit that was built and tested against
head_shaThe PR's head commit SHA at the time of testing. The schedule trigger compares this against the live GitHub value to detect whether the author has pushed new commits since the last run.
totalTotal number of test cases run
pass / failHow many passed and failed
behind_byHow many master commits the PR branch had NOT yet incorporated (before our local merge)
sync_statusGitHub's description: identical / ahead / behind / diverged
tested_as_syncedtrue = master was merged in before testing; false = merge had conflicts
merge_conflicttrue = there were git conflicts when we tried to merge master

8. How the website gets published

GitHub Pages is a free website hosting service built into every GitHub repository. When enabled, it serves the contents of a specific folder as a public website.

In our setup, GitHub Pages is configured to serve the docs/ folder of the tck_dashboard branch. Every time CI commits a new docs/drools-dashboard.html file and pushes it to that branch, GitHub automatically re-deploys the website within a few minutes. No web server to manage, no hosting costs.

The URL is: https://athirahari77.github.io/tck/drools-dashboard.html

9. How and when everything runs automatically

TriggerWhenWhat happens
Daily schedule Every day at 2:00am UTC Check upstream for open PRs. Test any PR that is new (no meta.json yet) or whose head SHA has changed since the last run (author pushed new commits). Regenerate dashboard.
Push to tck_dashboard (TestCases or runners changed) Whenever sync-upstream.yml pulls in new commits from upstream master Re-test all open PRs against the updated test cases. Regenerate dashboard.
Sync upstream workflow Daily (separate schedule) Pulls new commits from dmn-tck/tck master into our fork. If test cases changed, this triggers the push trigger above.

The chain works like this:

  1. Someone merges a PR in the upstream TCK repo, adding new test cases to master
  2. Our daily sync workflow picks up those changes and pushes them to tck_dashboard
  3. That push triggers pr-test.yml because files under TestCases/ changed
  4. All open PRs get re-tested against the new master state
  5. Dashboard is regenerated and published

10. How to trigger things manually

Go to: https://github.com/AthiraHari77/tck/actions/workflows/pr-test.yml

Click Run workflow. The input field accepts:

InputWhat it doesHow long it takes
Leave blank Only regenerates the dashboard HTML from already-saved results. No testing. ~1 minute
A PR number (e.g. 717) Builds Drools and runs tests for that specific PR only. Saves results and regenerates dashboard. ~30–45 minutes
all Builds Drools and runs tests for every currently open upstream PR. Saves results and regenerates dashboard. ~1–3 hours depending on number of open PRs
